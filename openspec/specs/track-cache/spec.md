# track-cache Specification

## Purpose
Повторно использовать найденные музыкальные ссылки и сохранять проверяемое происхождение трека без раскрытия данных другого чата.

## Requirements

### Requirement: Persistent provider aliases
Система SHALL сохранять набор найденных ссылок трека и находить запись по паре канонический провайдер–URL, включая сохранённые исторические адреса.

#### Scenario: Share a discovered service link
- **WHEN** пользователь присылает ранее найденную ссылку другого сервиса
- **THEN** поиск находит общую запись трека, а не создаёт независимый кеш по его названию

#### Scenario: Reopen the database
- **WHEN** приложение повторно открывает тот же сохранённый SQLite-файл
- **THEN** ссылки, алиасы и сведения о первом отправителе остаются доступны

### Requirement: Immediate checked cache response
Бот SHALL возвращать готовую проверенную запись без ожидания музыкальных API и пытаться запустить перепроверку в фоне.

#### Scenario: Cached track
- **WHEN** для ссылки есть ранее проверенная запись
- **THEN** пользователь сразу получает сохранённые ссылки, без сообщения «ссылка уже была» и без строки о работе кеша

### Requirement: Bounded background refresh
Система SHALL выполнять не более одной фоновой перепроверки одной записи одновременно и не более четырёх фоновых перепроверок всего.

#### Scenario: Repeated hits during refresh
- **WHEN** одну запись запрашивают несколько раз, пока её перепроверка выполняется
- **THEN** ответы возвращаются из кеша и второй параллельный запуск для этой записи не создаётся

#### Scenario: All refresh slots are busy
- **WHEN** все четыре места заняты
- **THEN** готовый ответ остаётся доступен, а следующий запрос может повторить попытку запуска перепроверки

### Requirement: Preserve valid links and fresh data
Система SHALL сохранять прежнюю ссылку при временной ошибке провайдера, удалять её при подтверждённом отсутствии трека и защищать свежие данные от устаревшей записи.

#### Scenario: Temporary search failure
- **WHEN** дополнительный сервис временно не отвечает при перепроверке
- **THEN** его ранее найденная ссылка сохраняется

#### Scenario: Definitive absence
- **WHEN** провайдер подтверждает отсутствие соответствия
- **THEN** его ссылка исключается из обновлённого набора

### Requirement: Earliest known sender and chat privacy
Бот SHALL сохранять наиболее ранние известные сведения об отправке и показывать отправителя и дату только в соответствующем исходном чате.

#### Scenario: Historical sender is imported
- **WHEN** импорт устанавливает более раннюю отправку, а кеш уже содержит свежие результаты поиска
- **THEN** происхождение уточняется без замены свежего названия и ссылок устаревшими данными

#### Scenario: Another chat requests a known track
- **WHEN** тот же трек запрошен в другом чате
- **THEN** ссылки доступны, но сведения о первом отправителе из исходного чата не раскрываются
