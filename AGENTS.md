# tbot project guidance

Project-specific guidance supplements the user's shared engineering instructions.

## OpenSpec

- Run the local CLI through `./scripts/openspec` (OpenSpec 1.16.1).
  Install its binary with `make openspec-install`.
- Generated OpenSpec skills and commands show `openspec` as shorthand. In this
  repository, invoke `./scripts/openspec` instead; the wrapper resolves the project
  root and keeps OpenSpec's machine state in the ignored `.cache/openspec/` folder.
- Read `openspec/config.yaml` and the affected `openspec/specs/*/spec.md` before
  planning changes to those capabilities. Verify existing behavior against source
  and tests, and surface any disagreement with a spec.
- For an explicit proposal request, use the proposal workflow and present its
  artifacts. For implementation, use the apply workflow within the scope the user
  authorized. User instructions and existing approvals take precedence over
  generated workflow defaults; do not infer permission to push, create a PR,
  deploy, or import production history from an OpenSpec task.
- Keep changes scoped. Update relevant specifications when behavior changes;
  use delta specs for work tracked as an OpenSpec change and synchronize them
  before archiving completed work.
- Run `make openspec-validate` for spec changes. Run the normal Go checks for code
  changes: narrow tests first, then `make test`, `make lint`, and `make build` when
  production paths are affected.
- `.agents/skills/openspec-*`, `.opencode/skills/openspec-*`,
  `.opencode/commands/opsx-*`, `.omp/skills/openspec-*`, and
  `.omp/commands/opsx-*` are generated by the pinned CLI. Refresh them with
  `make openspec-init`; keep project rules here and in `openspec/config.yaml`.
- Do not commit credentials, SQLite files, real chat exports, or personal history.

See `docs/openspec.md` for the workflow and tool-specific invocation syntax.
